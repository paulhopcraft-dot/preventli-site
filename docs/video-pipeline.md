# Partner-onboarding video capture pipeline

Turns the manual, undocumented, from-scratch process that produced
`public/welcome/*.mp4` into a runnable, versioned pipeline: Playwright
capture harness → ffmpeg stitch → ASR-gated verification. Built 2026-07-27
in response to the 2026-07-26 function audit
(`docs/onboarding-video-function-audit-2026-07-26.md`), which confirmed 6
video/product-drift defects and — separately — that no such pipeline
previously existed anywhere in either repo's history
(`docs/partner-onboarding-chapter2-rerecord-brief.md`'s "Pipeline research"
section).

**Read this whole document before running anything.** Several steps depend
on state in a *different* repo (`preventli`) and on an unmerged PR there.

---

## What this pipeline does NOT do

- **No TTS / voice generation.** No ElevenLabs (or any) API key is called
  anywhere in this pipeline. Paul's cloned voice is his to run — see
  "What needs Paul personally" below.
- **No editing of existing `.mp4` files.** Every existing file under
  `public/welcome/` was read (for reference parameters) and never written.
- **No production/live-partner data.** Every shot runs against the
  fictional `org-demo-partner` ("Vantage RTW Partners") tenant.

## Architecture

```
video-pipeline/
  reference-params.json        generated by probe-reference.mjs — the
                                exact codec/resolution/rate every existing
                                chapter agrees on; nothing downstream
                                guesses at these numbers
  capture/
    run.ts                     CLI: drives Playwright, records one .webm
                                per shot (native recordVideo context option)
    cleanup.ts                 CLI: removes the one client this harness
                                creates live, so re-takes start clean
    lib/
      demo-data.ts              casting constants (org, client, candidate)
      auth.ts                   one unrecorded login -> storageState, reused
                                 by every needsAuth shot except chapter 1's
                                 own (recorded) login
      recording.ts               the actual recordVideo + rename plumbing
    chapters/
      01-getting-started.ts
      02-setting-up-a-client.ts
      03-creating-and-sending-checks.ts
      04-candidate-experience.ts
      05-clinical-review.ts
    fixtures/
      generate-fixture-pdfs.mjs  synthetic placeholder JD PDFs (committed)
  stitch/
    probe-reference.mjs         ffprobe existing chapters -> reference-params.json
    stitch-chapter.mjs          per-shot .webm clips -> one chapter .mp4
    stitch-tour.mjs              chapters (+ intro) -> one full-tour .mp4
    mux-narration.mjs            attach a real narration track once one exists
  verify/
    verify-take.mjs             word-level ASR + per-gap volumedetect gate
  output/                       gitignored — everything this pipeline
                                 produces lands here
```

Every capture shot is a plain async function operating on a Playwright
`Page` — there is no dependency on the `@playwright/test` test runner or
its retry/reporting machinery, only the `playwright` browser-automation
library itself (`chromium.launch()`, `browser.newContext({ recordVideo })`).
This was a deliberate choice over `npx playwright test`: it gives full
control over shot ordering, naming, and per-shot output paths, which
`stitch-chapter.mjs` depends on (it globs `output/<chapter>/raw/*.webm`
sorted by filename — shot ids are numeric-prefixed, so filename order is
filming order).

## Prerequisites — read in order, all of this is unverified past step 2

This is the exact chain of things that have to be true, most fragile first.

1. **A Postgres reachable at `DATABASE_URL`.** `preventli/server/db.ts`
   throws at import if `DATABASE_URL` is unset — nothing in that repo runs
   without it. `preventli/docker-compose.yml` defines a `postgres:16`
   service on port 5432 (`gpnet-postgres`, user/pass `postgres`/`postgres`,
   db `gpnet3` — matches `.env.example`'s `DATABASE_URL`).
   **As checked 2026-07-27 in this environment: Docker Desktop's daemon is
   not running (`docker ps` fails, `dockerDesktopLinuxEngine` pipe not
   found), and `wsl.exe -l -v` shows both `docker-desktop` and `Ubuntu`
   distros as `Stopped`.** Per this machine's own history
   (`project_wsl_zombie_stack_decommissioned_2026_06_12` — WSL was
   deliberately decommissioned), this pipeline does NOT attempt to start
   WSL or Docker Desktop automatically. Starting `docker compose up -d` in
   `preventli/` (which itself needs Docker Desktop's WSL2 backend running
   first) is a manual prerequisite for whoever runs a real capture session.
2. **`preventli` checked out at a commit that actually has the fixes being
   filmed.** The `preventli` working copy on this machine, as found, is
   **detached HEAD at `8de6c7a`, several commits behind `origin/main`
   (`aa9be4c`)** — missing PR #339 (page-order fix), #340 (risk engine),
   #341/#343 (report-PDF fixes), #342. Capturing against the stale
   checkout would film pre-fix behavior, defeating the point. Whoever runs
   this needs `preventli` on `origin/main` (or a branch built on top of
   it) — **not** the detached HEAD this repo currently sits on. This repo
   (`preventli-site`) does not touch `preventli`'s working tree; that's a
   manual step in that repo.
3. **`preventli` PR #312 merged or checked out.**
   `server/seed-demo-partner.ts` (the `org-demo-partner` / "Vantage RTW
   Partners" seed) exists ONLY on branch
   `claude/preventli-onboarding-video-8a9c5d` — confirmed open and
   unmerged 2026-07-27 (`gh pr list` showed `#312  OPEN`). Without it,
   there is no demo tenant to log into and nothing in this pipeline works.
4. **Seed run once against that DB:**
   ```
   cd preventli
   npx tsx server/seed-demo-partner.ts
   ```
   Idempotent — safe to re-run any time to top up anything cleaned out.
5. **`preventli` app running and reachable:**
   ```
   cd preventli
   npm run dev
   # serves on http://localhost:5000 by default (PORT in .env.example)
   ```
6. **This repo's dependencies installed** (adds `@playwright/test` + `tsx`
   as devDependencies specifically for this pipeline):
   ```
   cd preventli-site
   npm install
   npx playwright install chromium   # only needed once per machine/version
   ```

Steps 1-3 could not be executed in this environment (no Docker daemon, and
this session does not have write access to the `preventli` repo beyond
reading). **Steps 4 onward were never run against a live app** — see
"What was and wasn't verified" below for exactly what WAS proven instead.

## Running a capture

```
cd preventli-site
npm run video:probe-reference        # regenerate reference-params.json from
                                      # the current public/welcome/*.mp4 files
npm run video:generate-fixtures      # (re)create the 3 placeholder JD PDFs

# one chapter:
npm run video:capture -- 02-setting-up-a-client

# a single shot within a chapter (for re-takes):
npm run video:capture -- 02-setting-up-a-client --shot 03-batch-upload-two-step-trap

# everything, in order:
npm run video:capture -- all

# watch it happen instead of running headless:
npm run video:capture -- 02-setting-up-a-client --headed
```

`capture/run.ts` refuses to start if `http://localhost:5000` (or
`CAPTURE_BASE_URL`) isn't reachable — it will not silently record a blank
page.

### Re-running a single shot

Most shots are self-contained (`page.goto` to a known route). A few assume
they're continuing from the previous shot's state within the same chapter
(documented at the top of each shot in the chapter file) and re-derive that
state themselves if run standalone — e.g. chapter 3's shot 03 re-fills the
form if it detects an empty `#candidateName` field. Chapter 2's batch-upload
shot (03) detects whether the JD-upload dialog is already open and, if not,
re-creates the client first.

### Re-running a full capture (idempotency)

- The 10 seeded clients + their JDs/checks: re-running
  `seed-demo-partner.ts` is a no-op (additive, `onConflictDoNothing()`).
- The ONE client this harness creates live on camera (chapter 2, "Northgate
  Distribution Centre" — see next section for why it's not "Coastline"):
  run `npm run video:cleanup` between takes to delete it, or the next
  capture run will create a second one with the same name.
- Chapter 3's check for Priya Nair: NOT cleaned up automatically. A second
  run creates a second in-progress check for the same candidate — harmless
  for filming purposes (the UI still shows one to send), but worth knowing.

## Casting — and one deliberate deviation from the rerecord brief

`docs/partner-onboarding-chapter2-rerecord-brief.md` casts "Coastline Aged
Care Group" / "Priya Nair" / "Personal Care Assistant" for the JD-pairing
beats, and its chapter-2 shot list literally says to type "Coastline Aged
Care Group" into the "Add a client" dialog.

That collides with the seed: `server/seed-demo-partner.ts` **already
creates a client named exactly that**, with Priya Nair's in-progress check
already attached. Typing it again in the "Add a client" dialog would create
a second, confusing "Coastline Aged Care Group" org (the seed is additive,
not a slate-wiper), and a second capture run would create a third.

This pipeline resolves it by **using a different, brand-new client name**
("Northgate Distribution Centre") for the "add a client" / batch-upload-JD
beats in chapter 2, and reserving the seeded "Coastline Aged Care Group" +
"Priya Nair" + "Personal Care Assistant" pairing for chapter 3, where it's
already correctly seeded with no invention needed. See the comment block at
the top of `capture/chapters/02-setting-up-a-client.ts` for the full
reasoning. This is a documented deviation, not a silent one — if Paul wants
the literal brief followed instead, that requires extending
`seed-demo-partner.ts` in the `preventli` repo to *reuse* Coastline for the
new-client beat somehow, which this PR does not attempt (out of scope: a
different repo, and the seed's own idempotency model doesn't have a clean
way to do it).

## A significant finding that changes chapter 4's scope

The audit's chapter-4 findings (stale "Page 9 of 9" counter, missing
90-question JD-driven middle, 26 role-fit questions extracted from a JD)
are about `DynamicCheckForm.tsx`, which only renders when an assessment
carries a non-null `formDefinition` (i.e. was created against a
`check_form_templates` row).

**A full search of `preventli` at `origin/main` (`aa9be4c`) — every route
file, the entire `POST /api/assessments` handler
(`server/routes/assessments.ts`, the exact endpoint the "Send a check" UI
flow calls), and every `.ts`/`.tsx` file repo-wide for `checkFormTemplates`
— found no code path that attaches a `formDefinition` to an assessment
created through the real, currently-live "Send a check" partner flow.**
The only three repo-wide hits are `server/storage.ts`, `shared/schema.ts`,
and one unit test — no route, no UI trigger.

Assessments created via "Send a check" (which is the only assessment-
creation path reachable from the partner UI that this search could find)
instead populate the legacy `preEmploymentAssessments` row, rendered by
`PreEmploymentForm.tsx` — an 8-step wizard ("Step X of 8": Personal
Information, Work History, Occupational Health, Medical Conditions,
Functional Capacity, Psychological Wellbeing, Family & Vaccination,
Lifestyle & Review), not the paginated 10-page JD-driven flow the audit
describes.

**Consequence:** `capture/chapters/04-candidate-experience.ts` films the
real, reachable 8-step form. It fixes defect #6 in spirit (shows the
substantive middle of a real multi-step form instead of just open+
signature) but does **not** and **cannot** reproduce or fix defect #4
(stale page counter) as literally described, because the counter this
harness can actually reach isn't the one the audit flagged. If the
JD-driven flow is reachable some other way this search missed (an
admin-only path, a PR not yet merged), re-point that chapter file at it
once confirmed — the file's own header comment has the full trail of what
was checked.

## Known gaps / unproven seams (read before trusting a "done" claim)

- **Never run against a live app.** No Postgres was reachable in this
  environment (Docker daemon down, WSL stopped, deliberately not started —
  see Prerequisites #1). Every selector in `capture/chapters/*.ts` was
  verified by **reading `preventli` at `origin/main`** (file:line citations
  in each file's comments), not by clicking through a running instance.
  The first real capture session should expect to fix at least a few
  selectors — the harness is built so that's cheap (`--shot` re-runs one
  shot at a time).
- **What WAS verified, mechanically, in this environment:** a smoke test
  (written temporarily, then deleted — not part of the committed pipeline)
  proved the actual moving parts work: `chromium.launch()` +
  `browser.newContext({ recordVideo })` produces real `.webm` files;
  `recording.ts`'s rename-to-shot-id logic works; `stitch-chapter.mjs`
  correctly transcodes+concats multiple clips into an mp4 that
  `ffprobe` confirms is byte-parameter-identical to the target
  (1920x1080, h264/yuv420p, 30fps, aac 48000Hz stereo) taken from
  `reference-params.json`; `stitch-tour.mjs` correctly concatenates the
  five real existing chapter files + intro into one 4:13 file matching
  the sum of their durations; `verify-take.mjs` fails loudly with exit
  code 1 and a clear message when no `GROQ_API_KEY`/`OPENAI_API_KEY` is
  set (confirmed both are blank in
  `C:/Users/Paul/.config/watch/.env` as of 2026-07-26/27) rather than
  silently skipping. The whole `video-pipeline/` tree also type-checks
  clean (`npx tsc --noEmit`, zero errors).
- **`stitch-tour.mjs` prints a "Non-monotonic DTS" warning** when
  concatenating the five independently-produced existing chapter files —
  cosmetic (ffmpeg auto-corrects it, `-c copy` output plays fine), not
  something this pipeline introduces; a naive concat of independently
  encoded sources commonly does this.
- **Chapter 1's trial-signup footage is out of scope.** Only login +
  workspace tour are automated; signing up fresh needs a real inbox to
  click an email-verification link, which nothing here attempts.
- **Chapter 5 cannot be filmed end-to-end by this harness alone.** Getting
  a report into "awaiting your approval" state requires GPNet clinical
  review first — a different actor/role with no seeded login in
  `seed-demo-partner.ts` (partner-only seed). There is also a live, open,
  documented bug in the way regardless: the audit records `reportUrl`/
  `questionnairePdfUrl` as NULL after submission ("still open as of this
  writing"). `chapters/05-clinical-review.ts` fails loudly (doesn't hang,
  doesn't fake data) if the approval card never appears.
- **`npm install` surfaced 19 pre-existing vulnerabilities** (1 low, 4
  moderate, 12 high, 2 critical) via `npm audit` — not introduced by this
  PR's two new devDependencies specifically (not verified either way;
  flagging rather than claiming either way since `npm audit` doesn't
  attribute per-package by default in its summary output). Worth a
  separate look, not blocking this PR.

## Verification gate (`verify-take.mjs`)

Rebuilds, as an actual committed script, what `chapters.ts`'s own comments
describe but that was never saved anywhere: word-level ASR timestamps +
a per-gap `ffmpeg volumedetect` silence check, edge-trimmed 60ms.

```
GROQ_API_KEY=... npm run video:verify -- video-pipeline/output/02-setting-up-a-client/02-setting-up-a-client.mp4
```

**No silent skip when no key is configured** — confirmed by running it
with both `GROQ_API_KEY` and `OPENAI_API_KEY` unset in this environment: it
exits 1 with an explicit message, matching the brief's instruction not to
have the check quietly do nothing.
